# 客户端并发数与请求节奏（推算方法写清，未测的直接标未测）

## 1. 客户端侧能算出来的：有效吞吐

`results/20261111T155607-v0.2.4/logs/21-browser-transfer.log` 里每 5s 一条 `解密块 N/1024` 进度：
- 59 个进度点，从 `107/1024 @128.7s` 到 `707/1024 @418.8s`；
- **平均 2.07 块/秒**，中位 2.20 块/秒，峰值 4.80 块/秒。
- 与 `TransferReadPerIP = 120/60s`（2 块/秒）**几乎贴着天花板** → 说明瓶颈是限速，不是带宽、不是磁盘。

## 2. 并发数：从服务端相邻请求时间戳反推

现场抓的服务端 chunk 行（`docker compose logs yanshu-server`，原始串）：

```
16:04:37.724Z 200
16:04:37.767Z 200     Δ=43ms
16:04:37.812Z 200     Δ=45ms
16:04:37.858Z 200     Δ=46ms
16:04:37.901Z 429     Δ=43ms
16:04:42.910Z 200     Δ=5009ms   ← 撞限速后等了 ~5s
16:04:42.954Z 200     Δ=44ms
16:04:42.995Z 200(burst 结束)
```

判读：**请求是 43–46ms 等距成簇（每簇 4–5 条），簇与簇之间被一次 429 打断、随后 ~5.0s 才恢复**。
- 每簇 4–5 条、间隔 44ms ⇒ **同时在飞的请求约 4–5 条**（若严格单飞，间隔应≈响应耗时 2–3ms，而不是 44ms；
  44ms ≈ 单块 1 MiB 的解密+校验耗时 → 说明客户端**按 4–5 个 worker 轮流发、每个 worker 串行**）。
- 也就是说：**并发只有 4–5，不存在"并发过高把服务端打挂"**；被限速的是 IP 级 2 块/秒的窗口额度。

> 方法学说明：并发数是**反推**（相邻时间戳差 + 每块处理耗时），不是直接读客户端连接池数——
> 客户端没有日志暴露 inflight 计数，浏览器 network 面板也没抓。这是本次能量到的上限。

## 3. 1024 块到底什么时候拉完（与 Core 的分歧点）

- `TransferReadPerIP` 2 块/秒 ⇒ 1024 块至少 512s；实测块速率 2.07 块/秒 ⇒ 预计在 **~570s** 拉完最后一 块。
- 脚本在 **421s** 因「download 事件」5 分钟超时改为轮询 `downloads/` 目录，**但没有停**（继续轮询 40 分钟）。
- 所以：Core 说的「1024 个 200 发生在脚本放弃之后」——**时间顺序对，结论不对**：脚本没放弃，只是换了个等法；
  而且我事后统计的 `N200=1024`（该栈只跑过这一条 1 GiB 传输）说明**块确实全部到手**，缺的是最后落地那一跳。
