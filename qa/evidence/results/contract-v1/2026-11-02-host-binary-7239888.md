## 4. 升级路径（上一轮的 P0 已修，实测）

用**老二进制 `08d40e7`**（其 `0001_init.sql` 里没有 kid 列）先建库，再升级到 `7239888`：

| 步 | 结果 |
|---|---|
| 老库建成（`08d40e7 -migrate-only`） | `upload_token_kid` 列 **不存在**（count=0） |
| 新二进制 `-migrate-only` | 应用 `0001/0002_upload_token_kid/0003_token_kid_state` |
| 升级后 | 列 **已存在**；服务能起（日志有 `listening`，无 `sweep failed`） |

**结论：迁移补上了幂等 ALTER，已有库升级不再缺列。** 唯一要求是升级时跑一次
`-migrate-only`（服务启动本身也会跑）。

## 5. token 四步（同一二进制，`gate_723` 全新 schema）

| 步 | 状态 | 错误名 |
|---|---|---|
| ① 基线（secret-A, kid=1） | **201** | — |
| ② 只换 secret（kid 不变） | **401** | **`AUTH_TOKEN_INVALID`** |
| ③ 只换 kid（secret 不变） | **401** | **`AUTH_TOKEN_STALE`** |
| ④ 换 kid 后新签发 | 新 token **201** | — |

旧 token **不复活**：③ 后把 ② 的 token 再打 → 401 `AUTH_TOKEN_STALE`；
④ 后把 ① 最初的 token 再打 → 401 `AUTH_TOKEN_STALE`。

> 错误名以**实现**为准：本轮实测是 `AUTH_TOKEN_INVALID`（secret）与 `AUTH_TOKEN_STALE`（kid）。
> 契约方最新稿写的是 `AUTH_TOKEN_REVOKED`，**两边尚未统一**——统一后我复测一次即可，
> 脚本判的是状态码 + 是否被拒，不依赖名字。
