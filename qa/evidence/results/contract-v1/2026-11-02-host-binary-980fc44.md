## 3. token 生命周期实测（最小实验）

**问题**：轮换 `YANSHU_TOKEN_SECRET` 后，已签发的 `upload_token` 会不会失效？

**做法**：同一 schema 上起两次实例（同一端口由脚本各取空闲端口），
第一次 `TOKEN_SECRET=a…` 建传输拿到 `upload_token`，第二次换 `TOKEN_SECRET=b…` 重启，
用**旧 token** 打受保护端点 `PUT /v1/transfers/{id}/prelude`。

**结果**：`HTTP 201` —— **旧 token 仍然可用**。

**结论**：轮换 `TOKEN_SECRET` **不会**吊销已签发 token；token 的校验依据是库里的 SM3 记录，
与 secret 无关。因此**"secret 泄露 → 一键吊销"目前做不到**，只能靠库层删除/过期。
这与我们此前"重启即失效"的假设不符，属**真实缺口**（Core 已在加 `kid`/epoch）。
复跑（已脚本化）：

```sh
python3 qa/evidence/check_token_lifecycle.py \
  --binary <yanshu-server> --dsn "<DSN>&search_path=gate_ev1" --ys-tool <ys-tool>
# 输出末行即结论：旧 token 仍可用 / 已失效
```

`kid`/epoch 落地后应改成「轮换 → 旧 token 立刻 401、新 token 200」，并在 `results/` 留一份新结果。

### token 三组对照（在 `08d40e7` 上重做，逐组只改一个变量）

| 组 | 改了什么 | 实测 | 判读 |
|---|---|---|---|
| 基线 | 不变 | **201** | token 可用 |
| **A：只改 `TOKEN_SECRET`** | secret A→B | **401 `AUTH_SIGNATURE_INVALID`** | **secret 轮换即吊销** |
| **B：只改"版本"**（`YANSHU_TOKEN_EPOCH=1→2`，secret 不变） | 试一个契约外的版本变量 | **204 → 204**（均为"已上传、接受"） | **该变量被忽略**：`08d40e7` 上**没有** epoch/kid 机制 |
| **C：改 secret 后重签发** | 新建传输拿新 token | **201** | 吊销后可恢复 |

结论（措辞要分清两件事）：

1. **这个 commit 上没有 epoch/kid**：`server/` 里 `grep -i epoch|kid` 零命中，`YANSHU_*` 环境变量
   清单里也只有 `YANSHU_TOKEN_SECRET`（没有 `YANSHU_TOKEN_EPOCH`/`KID`）。所以"只改版本、
   不动 secret"这条**在当前实现里不存在**，不是"实现了但没生效"。
2. **吊销手段就是轮换 `TOKEN_SECRET`，并且实测生效**：`Validate` 用当前 secret 重算后再与
   库里 `SM3(token)` 比对（`auth/token.go`），所以换 secret → 旧 token 立刻 401。
3. 因此"只改 secret → 旧 token 仍 201（设计如此）"这一假设**不成立**；上一轮我在 `9065eb8`
   上测到 201，是因为那版 `Validate` 只比哈希、确实没修——两轮结论不矛盾。

> 待对齐：401 的错误名是 `AUTH_SIGNATURE_INVALID`，而契约澄清稿规划的是 `AUTH_TOKEN_STALE`
> （EPOCH 旧版本）。名字统一前前端只能按 401 兜底。

复跑：`python3 qa/evidence/check_token_lifecycle.py --binary <bin> --dsn "<DSN>&search_path=…" \
        --ys-tool <ys-tool> --epoch-check`（`--epoch-check` 就是上表 B 组）。
