# ADR-0001 · 块序号 / 总块数 / 末块标志与 AAD 的关系

| 项 | 值 |
|---|---|
| 状态 | **提案（未采纳进 v1）**；v1 维持现状，增强留待版本升级 |
| 日期 | 2026-11-03 |

| 关联文档 | `docs/CRYPTO-PACK.md` §6.4（nonce 构造）、§7.2（`AAD_CHUNK`）、§7.3（`AAD_MANIFEST`）、§8.4（摘要口径）、§13（接收方校验矩阵） |

---

## 1. 背景

篡改检测测试中有两个容易被误读的现象：

1. 端到端篡改用例里，多数场景会**先被清单层拦下**，取不到块级 tag 失败（实现内部可能另起名，如 `TAG_MISMATCH`）；
2. 因此产生一个疑问："块序号到底有没有被 AEAD 认证，还是只靠清单摘要兜底？"

本 ADR 把这件事一次说清：核对现状、界定残余风险、给出只在**未来版本**才考虑的改法，避免有人在 v1 上就地改字段。

---

## 2. 现状核对（`YSPK/1.0`）

`CRYPTO-PACK.md` §7.2 定义的 `AAD_CHUNK` 是**固定 32 字节的结构化输入**（全部大端、无填充）：

```
AAD_CHUNK = 0x01 ‖ "YSPK" ‖ VERSION_MAJOR ‖ VERSION_MINOR
          ‖ u32be(CHUNK_SIZE) ‖ u32be(CHUNK_COUNT) ‖ u64be(PLAINTEXT_SIZE)
          ‖ u32be(CHUNK_INDEX) ‖ u8(LAST_FLAG) ‖ u32be(PT_LEN)
```

| offset | len | 字段 | 与"块位置"的关系 |
|---:|---:|---|---|
| 0 | 1 | `AAD_LABEL` = `0x01` | 域分隔（块 vs 清单） |
| 1 | 4 | `MAGIC` = `YSPK` | 格式身份 |
| 5 | 1 | `VERSION_MAJOR` | 版本身份 |
| 6 | 1 | `VERSION_MINOR` | 版本身份 |
| 7 | 4 | `CHUNK_SIZE` | 块长口径 |
| 11 | 4 | `CHUNK_COUNT` | **总块数** |
| 15 | 8 | `PLAINTEXT_SIZE` | 明文总长 |
| 23 | 4 | `CHUNK_INDEX` | **块序号** |
| 27 | 1 | `LAST_FLAG` | **末块标志** |
| 28 | 4 | `PT_LEN` | 本块明文长 |

**结论：三项（块序号、总块数、末块标志）在 v1 已全部纳入 AAD**，并且块序号**同时**进入 nonce（§6.4：`u64be(index) ‖ 00 00 00 ‖ LAST_FLAG`）。因此：

| 篡改 | 在哪一层失败 | 机制 |
|---|---|---|
| 交换两块顺序 | AEAD 层 | 密文换位后，其 AAD 的 `CHUNK_INDEX` 与实际位置不符 → tag 校验失败 |
| 删除中间块 | 块结构层 + AEAD 层 | `CHUNK_COUNT` / `LAST_FLAG` 与实际块集不符 → `CRYPTO_CHUNK_ORDER` / `CRYPTO_CHUNK_MISSING` |
| 截断尾块 | 同上 | 找不到唯一 `LAST_FLAG=1` 且 `INDEX == CHUNK_COUNT-1` 的块 |
| 搬入别的包的合法块 | AEAD 层 | 每包独立 `DK`/`KDF_SALT` 派生 `KEK_CHUNK`，他包块在本包密钥下认证必失败 |
| 单字节密文篡改 | AEAD 层 | GCM tag 不符 |

所以"仅靠清单摘要兜底"的说法**不成立**：清单摘要（§8.4）是第一道冗余防线，块级 AEAD 是第二道，两道都在。

---

## 3. 残余风险（真实存在，但与"块序号是否进 AAD"无关）

**R1 · 包身份没有以明文字段形式进 AAD。** 跨包搬运的拦截依赖"每包 `DK` 与 `KDF_SALT` 独立"。若某次实现为了"重打包/续传"复用 `DK`，跨包搬运就会退化为 nonce 复用，可能出现灾难性后果（同密钥同 nonce 下 GCM 的机密性与完整性同时崩）。

**R2 · 错误码取决于实现顺序。** 若实现把"逐块摘要比对"提到"块级 GCM"之前，同一篡改用例会得到不同错误码。测试判定只应看"是否拒绝"，不应绑定具体错误码。

**R3 · 头字段与 AAD 的一致性需要显式交叉校验。** 若实现信任自己解析出的块数/总长，却不与 AAD 输入比对，则"谎报块数"仍可能被接受。§13 第 19–22 条要求逐项校验，实现不得省略。

---

## 4. 提案（仅面向未来版本）

### 方案 A（推荐，若要做）

在 `AAD_CHUNK` 末尾追加 `KDF_SALT(16)`，把**包身份**显式绑进 AEAD。

- **格式影响**：`AAD_CHUNK` 32 → 48 字节；**所有包字节随之改变**；`SIG_SEC` 会因 `HDR_CORE`/清单未变而不变，但样例、测试向量、交叉验证基线必须全量重算。
- **版本策略**：必须抬版本号（`VERSION_MAJOR` 或 `VERSION_MINOR`），**不可就地改 `YSPK/1.0`**；旧实现读到新版本必须按 §2.2 拒绝，不做兼容猜测。
- **收益**：即使 `DK` 被误复用，跨包搬运也会在 AAD 层失败；审计时"包身份是否被认证"一眼可查。
- **成本**：端侧、服务端（只透传不解析，影响小）、测试向量、跨实现对照基线全部同步一次。

### 方案 B（不改格式）

维持 32 字节 AAD，把 R1/R2/R3 落成实现侧的硬要求与测试项：

1. `DK` 与 `KDF_SALT` **每包必须新取**，任何"重打包再用旧 `DK`"的实现路径都视为缺陷；
2. 块级 GCM 校验**先于**逐块摘要比对（与 §13 次序一致）；
3. 头字段（`CHUNK_COUNT` / `CHUNK_SIZE` / `PLAINTEXT_SIZE` / `LAST_FLAG`）必须与 AAD 输入逐项交叉校验；
4. 测试矩阵为 R1–R3 各加一条负例（密钥复用、错误码顺序、头字段谎报）。

---

## 5. 结论

1. **v1（`YSPK/1.0`）不做任何改动**：块序号、总块数、末块标志已在 `AAD_CHUNK` 内（§7.2，offset 23 / 11 / 27），改 AAD 只会让已冻结的格式与既有实现错位，收益不足以抵消重冻成本。
2. 方案 A 留待**版本升级**评估；届时必须走 ADR + 版本号升级 + 全量样例重算 + 端侧/测试同步。
3. 方案 B 的三条不改格式，可直接作为 v1 的实现检查项与测试负例，不需要等版本升级。
